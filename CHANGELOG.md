# Changelog

All notable changes to this project are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and Semantic Versioning. Team bundle versions evolve independently of DeepSeek Harness versions; DeepSeek Harness compatibility is expressed through `peerDependencies` and [`docs/dsh-release-compatibility.md`](docs/dsh-release-compatibility.md).

## [Unreleased]

- Team Board 8/10 (#124): the Team Inbox becomes Multica's inbox. The queue is grouped by what it asks of the reader — 「必须处理」 (a pending decision card from #109, or a Task waiting for the Human's accept), 「需要关注」 (a mention of the reader, or a failed Turn) and 「动态」 (everything else) — and each band prints its own count, with no heading for a band that holds no rows. The severity is derived, never stored: the Host's own projection says who was mentioned, and two side reads (the Thread's open decision cards and its failed Turns) say what else waits, so a row settles into its band when those reads land. A row carries its band's word in the band's own ink (「待你决策」, 「等你验收」, 「提到你」, 「有 Turn 失败」, 「有新动态」), so a row that must interrupt reads as one before its gist is reached. The header carries Multica's facet menu — unread, severity, channel and agent — each with the count that facet can reveal, computed with the ported `multica/inbox-filter.ts` helpers the list filters by, so the menu and the list cannot disagree. On a seat at least 720px wide the page splits: the queue on the left, the selected row's task detail on the right, with the Task's own properties (status, priority, assignee, the people on it), the reason the row is in the queue, the failed Turns it carries, and an open decision card answered in place. A plain click selects the row into the detail pane and a modifier click opens its Thread; on a narrow seat the click opens the Thread and the detail follows it full-screen. Read and archive are the reader's own operations: marking read goes through the durable Thread read the queue already drains through, and archive is the unfollow — offered only where an unfollow can land. The arrow keys walk the rows and move the selection instead of opening a Thread, skipping the band headings. The new `tests/inbox.client.spec.tsx` covers the bands, a decision answered out of the action-required band, the filters and their counts, the durable read, the archive, the split view and the narrow-seat behaviour; the existing inbox specs keep passing.

### Team Board

- Team Board 10/10 (#135): the stack closes with what a reader needs on top of the features. One end-to-end browser journey (`npm run test:browser`) walks the whole flow: a Task created on the board, handed to a Worker, watched while its Turn runs, stopped from the execution log, claimed by the Worker, reviewed and accepted by the Human, with the Agent's own page showing the run and the tokens it spent. A bilingual user guide (`docs/user/team-board.md`) covers the roles and their setup, the board and its drag rules, the task detail and the execution log, Stop versus Chat, the Overview, the Inbox severities, the Orchestrator digest configuration and the Multica attribution. An architecture note (`docs/architecture/team-board-runtime.md`) records the new seams: the `team/task-created` and `team/task-updated` op kinds, the `workspaceActivity` aggregate, the digest timer and the Multica reuse policy with its pinned upstream commits.
- Team Board 9/10 (#134): a Member with the role `orchestrator` watches the team and reports on it, and never acts. The role is a fence, not a prompt: `team_claim` is withheld from the Orchestrator's tool surface (absent from the request, refused on a surface that predates the role) and `team_message` with `asTask` is refused for it, so it can read, post, ask and answer but cannot change Task state, hold a Direction Claim, or steer another Member. The new read-only `team_activity` tool is the snapshot behind the digest: per-agent state (presence, running turn, current Task, idle minutes, turns, tokens and failed turns inside the window), Tasks by status with their open rows and age, open decision cards, and the window's top events, bounded with an explicit truncation marker on every cap it crosses. The digest itself runs on a Host-side timer — not the Harness schedule service, whose reminders bind to one Session id while a Member's Session changes on rollover — configured by a new `digest` section on the Team Host row (`enabled`, `intervalMinutes` default 1440, optional `dailyAt`, `channel` default `team-digest`); every field is volatile, so enabling, disabling or retiming it lands on the running Host without a restart. Each tick creates the digest Channel when it is missing, wakes every idle Orchestrator with one report-only prompt, and skips a busy one so a digest never steers a running turn. The Orchestrator's model is its own Member model, so a cheap model is the right one. The interval is capped at 35,791 minutes and the armed delay is clamped, because a larger `setTimeout` is silently clamped to 1 ms and would wake continuously; each tick delivers at most one digest per Member, and the prompt names its Workspace, so a seat in several Workspaces is neither steered twice nor left guessing which one to read.
- Team Board 6/10 (#124): the Agents tab and the Agent detail page become Multica's Agent surfaces. Each roster row now carries the Agent's avatar with a derived presence dot, handle, role pill, the Task it is on (`#n` + title, from the live Turn's Thread or its first active Claim), the tool it is running right now from `memberActivity`, instance load (`busy/total`) and today's tokens from `memberSessions`. The toolbar keeps search, role and presence always visible instead of a filter popover, since the roster is small and fully local. The detail header shows avatar, handle, role, presence, model, the current Task as a link and the live current tool, with two actions that stay reachable from every tab: **Chat** opens the Member's own dsh Session, and **Stop** confirms, then cancels slot 0 and every working instance through `session.cancel` (reusing the 5/10 `stopSession` prop) and is disabled while idle. `AGENT_VIEW_IDS` gains `runs` and `tasks` beside sessions, config and memory: the Runs tab ports Multica's activity tab — `memberSessions` rows (started, duration, turns, tokens in/out, cache, tools, model, Threads), a 14-day token `Sparkline`, and failure chips from `threadTurnFailures` via the ported `task-failure.ts` — and a row opens its Session; the Tasks tab groups the Tasks the Member is assignee or active Claim owner of by status and reuses `BoardCard` in a compact, read-only face. Pure derivations live in `agents/agent-page-model.ts` so the row and the header cannot disagree, with a new `tests/agent-page.client.spec.tsx` covering the row's tool and role pill, the presence filter, the header's current Task, Stop's idle and busy paths, Chat, and both new tabs, plus `tests/agents/agent-page-model.spec.ts` pinning the pure derivations behind them. A browser journey drives the same path in the real shell: the roster row in the Team Settings page, the presence filter, the Agent's own Session with its Runs tab, and the gated Stop.
- Team Board 5/10 (#124): the Thread page becomes a Multica-style issue detail. A new Execution log section (ported from Multica's `execution-log-section` + `inline-comment-run`) renders each seat's Session runs for the Thread from the Host's `threadSessions` Remote — the active run first with a live elapsed clock and its current tool and step count from the `memberActivity` snapshot, past runs with duration, token flow (`in → out`), cache, tool and turn counts and the model, and failed Turns flagged from `threadTurnFailures`. A run row opens the seat's native Session; Stop sits behind a confirm dialog and goes through the dsh Session controller (`session.cancel`), with a non-optimistic "stopping…" state that clears when the Host folds the run out of the active set. The section follows both the Thread's and the activity's change scopes, so finishes and step progress arrive live. The page is restyled after Multica's issue detail: a breadcrumb header (`Workspace / Channel / Task #n`) with an inline title editor (Enter saves, Escape cancels, stale-revision refetch), Status/Priority/Assignee pickers as sidebar property rows (Task fields from Board 1/10; `in_progress`/`in_review` stay claim-derived), claims as a disclosure in the same sidebar, followers, created and last-activity rows, and the properties column folds into a sheet under 768px. The read path gained a fix: the passive refresh on a change wake could resurrect a stale projection (pre-drain React state) and stall the automatic unread drain on a phantom unchanged remainder; it now bases its merge on the synchronous projection ref. New spec `thread-detail.client.spec.tsx` covers the log rows, the stop flow, the pickers, the title edit and the sidebar.
- Team Board 4/10 (#124): the Team gains the Board — a Multica-style kanban opened from the strip's new `看板` tab (`Tasks | Board | Team | Agents | Scheduled`; the tab body is the open action that hands the seat to the board face). Five fixed status columns built from the Workspace catalog; cards show `#taskNumber`, title, priority, the Channel pill, the assignee avatar, the Task's Claim direction and a live agent-activity badge fed by the `memberActivity` snapshot (refreshed on the `activity` change scope). The create dialog (新建任务) mints an unassigned Task with `createTask` — assignee defaults to Unassigned, the Channel defaults to the last one used (remembered in this browser). Drag rules are the collaboration model's: a drop to `done`/`closed` (or back to `todo`) calls `changeTask` with `accept`/`close`/`reopen`; a drop to `in_progress`/`in_review` is rejected with the claim hint; a same-column drop persists a `position` via `updateTask` (a column whose neighbours tie is renumbered 1..n). Dragging works with mouse, touch (250ms hold) and keyboard, with announcements in the interface language. The house rule holds — no optimistic mutations: the card moves only after the Remote commits and the change wake refetches, a refusal snaps it back with an inline notice, and a stale revision or an unread Thread (ordinary `ok` answers from the Host) each get their own notice. Filters (Channel, assignee incl. Unassigned, priority, text) and per-column hiding (localStorage) round out the page. Client only; the ported board files carry the Multica derivation header, and `docs/frontend-design/board.md` documents the surface. The board follows the scope-less change stream, because Task commits wake only Channel and Thread scopes, so an Agent's claim or another client's edit moves a card without a reload. The create dialog is a dsh `Modal`, retries reuse their request id, and a card is one tab stop whose title opens the Task while its pickers never do.
- Team Board 3/10 (#124): the shared Multica-look components land in `src/client/multica-ui/` — `StatusIcon`, `StatusHeading`, `PriorityIcon`, `ProgressRing`, `ActorAvatar`, `AgentAvatarStack`, `AgentPresenceDot`, `AgentActivityIndicator`, `StatusPicker`, `PriorityPicker`, `AssigneePicker`, and the shared `PickerMenu`/`PickerItem` shell. The status picker offers the ledger's five statuses but enables only the three human targets (`todo`, `done`, `closed`); `in_progress`/`in_review` render disabled with the claim explanation. The activity badge reads the `memberActivity` snapshot (current tool, step and tool counts, turn start) and opens a dsh `HoverCard`. The parity audit now walks subdirectories, so the new sheets follow the same focus, token and geometry rules as the top-level sheets. `docs/frontend-design/multica-look.md` lists every component and its Multica origin. The picker shell portals its list, names its trigger `field: value`, marks the selected row with `aria-current`, points disabled rows at one visible hint, and stops the trigger's click from reaching a clickable card; `PriorityIcon` `inheritColor` now really inherits; an assignee the roster no longer lists shows its id instead of "Unassigned"; the activity badge opens its details on keyboard focus and speaks for the most recent Turn; every ported stylesheet carries its derivation header. This layer also changes `member-row.module.css` (`corner-shape: round`) and types the `multica/{status,priority,presence}.ts` tables `as const satisfies`.
- Team Board 2/10 (#124): a Member now carries an optional `role` (`architect|leader|worker|orchestrator`), set when it is created or edited and shown as a pill in the roster. The role is a display and prompt fact, never a routing rule: it appends one fixed section to the Member's identity block (`MEMBER_ROLE_PROMPTS`), and a Member without a role renders exactly the prompt it had before. `addMember` accepts `role`; `updateMember` changes it, and `null` clears it. The editor dialog, the Agent Config tab and the create form share one native role select. No new ledger kind: the role rides the existing `team/member-added` and `team/member-updated` records, and older ledgers without it replay unchanged. A role outside the four is refused at commit, an unknown role from a newer Host shows no pill instead of a blank one, and the empty option reads "Not set"; the Leader prompt no longer tells it to "mark in review", which no tool does.
- Team Board 1/10 (#124): a Task now carries the fields a board needs — `title` (falls back to the opening Message's first line), `priority` (`urgent|high|medium|low|none`, default `none`), `assignee` (`MemberId | null`, independent of Claims) and `position` (fractional order within a status column). Two Human Remotes create and update them: `createTask` creates an **unassigned** Task with an opening Message in one commit, and `updateTask` patches title, priority, assignee or position without touching status. Assigning a Task to a different Member appends a public `assign` Activity, which starts the assignee's Attention when needed and is unread for it, so `notifyMember` wakes it; `null` clears the assignment. `createTask` without a `position` places the Task after its Workspace's todo column, `priority` is validated before it is stored, an assignee is stored by its canonical Member id, and an attachment on a board-created Task is listed for agents like any Message attachment. `updateTask` is fenced by the Thread revision alone, and field-only edits append no fact and leave that revision unchanged. Two new ledger kinds (`team/task-created`, `team/task-updated`) with replay validation, change scopes, room-activity summaries and idempotent retry. Status is still derived from Claims; `in_progress`/`in_review` are not writable here.
- Team Board stack base (#124): the client gains the Multica look layer (`multica-look.module.css`, a scoped `--ml-*` surface mapped onto `--dsw-*`), the ported pure helpers the board, Task detail, Agent pages, Overview and Inbox share (status, priority, drag/position, sort, filter, presence, inbox filter, time-ago, run labels) with node-environment specs, and the board dependencies (`@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities`, `react-virtuoso`). `NOTICE`, `licenses/MULTICA-LICENSE` and a Team Settings → About line carry the Multica License attribution. ### Other changes

- Plan to description (M-39): a plan proposed on a Task becomes that Task's description once the Human approves it. The new `team_plan` tool proposes a plan on a Task that is still being designed — one plan per Task, and only while the Task is `todo` and holds no active Claim, the planning phase the issue view answers as `properties.planningPhase` — writes its sections, submits it for the Human's review, and reports the plan's state. The plan is a Doc bound to the Task, so the approval is the Doc's existing review verdict and its mention wakes the proposer: no new operation kind and no new issue entity. The approved plan replaces the description, and the description becomes a record of its own — the body, where it came from, the plan it came from, who wrote it and when. The description has its own fence: its two writers, the Human's inline edit and the plan's promotion, serialize on `descriptionRevision` rather than on the Thread revision, and a stale fence is a business outcome (`stale_description_revision`), the same shape as `staleRevision`. The approval is two writes, so the second can be lost, and the convergence is order-based: the repair runs when the last description write is older than the approval, so a Human edit made after the approval is never clobbered, a retry resolves the stored operation instead of colliding, and a failed repair never fails the read.
- Issue view (M-35): the client grows the issue surface — the seven regions of the Host's `issueView` snapshot, rendered as a props-only tree in `src/client/issue/`: the header (the Host-resolved title, the `#n` identifier, the status, and the inline title editor), the description record (read-only here — its write path and its own fence are M-39's), the properties column (status, priority, assignee, the dates, each with its picker, writing through the Human's `updateTask` / `changeTask` paths), the comment thread (the Host's Messages, oldest first, with one-level replies and the next page through `threadHistory` — read from the merged cursor, so a page is never fetched twice, and with the Thread's anchor and every decision's ask left out, exactly as the Host's own issue read leaves them), the activity (the newest fifty, with the tail indicator), the decisions (the ask cards and the recorded decisions, one row each) and the execution log (the already-ported Thread log, so the live row and its Stop keep working). The navigation snapshot gains an orthogonal issue slot — `issueRef` and `issueVariant` — so the issue opens **over** the face the reader is on instead of replacing it, and closing it returns them to it; the page presentation is the whole column, the slice dialog over the live face is M-38's chrome over the same tree, and the narrow width folds the property column into a dsh `Modal`. The readSnapshot fix travels with it: the Task identity is restored independently of the Thread branch, so a position that carries a Task and no Thread — the issue position — keeps its Task across a reload.
- Issue view contract (M-34): the Host grows one read model for an issue — the `issueView` Remote returns the seven regions of one Task in one snapshot: the title and the description record, the board properties, the newest comments, the activity, the decisions, the execution log, and the Docs bound to the issue. The contract carries no variant: the page face, the slice dialog and the peek panel read the same value and render different subsets of it, and `commentLimit` is a read size, not a presentation flag. The Host decides what the client reads: the title is resolved once (`task.title ?? the anchor's first line`), the description is a record with its own fence (`description.revision`, not the Thread revision), and the planning-phase answer — `todo` and no active Claim — is computed in the ledger and carried as `properties.planningPhase`, so the client never re-derives the rule (`isPlanningPhase` only reads that answer). The decisions region carries every ask card exactly once and every recorded decision exactly once: a card with no record is a card row, a record is a decision row that carries the card it came from, and the ask message is not a comment — the card renders in its place. A Doc can now be bound to a Task (`AgentTeamDoc.taskRef`), explicitly rather than derived from the Thread, so a plan is identifiable in the issue's `docs` list. The Client seam is one query keyed `issue:<workspace>:<task>`, covering the issue's Thread and its Workspace, and the read is async: it converges before it answers, and a failed convergence never fails the read.
- Team Detail page (M-50): the side menu's `Team Settings` row becomes `Team Detail` (团队详情), one page that carries the team's surfaces behind a sub-nav — `Overview` (总览), `Agents`, `团队记忆` (Team memory) and `设置` (Settings) — the way Multica's own detail pages switch their sections. The Workspace picked above the sub-nav scopes all four. The host's `Overview` tab is gone with it: the strip reads `Tasks | Teams | Scheduled`, the workspace Overview is the Team Detail page's first section, and the Team browser's own Overview card and rail button are retired, so the Overview has one home. The page keeps the panel id `agent-team-settings` (the host may persist the selected panel, and the patched codex-ui keys its top-level list on it)…
- Owner decision records (decision cards #87 follow-on): the Team ledger records the Human's decisions on a Task as first-class facts — who decided, what was decided, why, when, and the source it came from (the ask card they answered, or the plan they approved). A record is not a second write: it rides the operation that already records the decision (the answer, the verdict), so one decision is one operation and therefore exactly one record, and no ledger state exists in which the decision is committed and the record is missing. The write points are exactly two — the Human's answer to a decision card and the Human's approval of a plan; an ask, a withdrawal, a request for changes and a cancellation record nothing. A record is immutable: a changed mind is a new record (a second plan approved on the same Task supersedes the earlier one), and the record it supersedes stays listed. A decision taken on a Thread with no Task is still recorded, and it joins the Task when the Thread is promoted. Operations written before records existed are derived from the notice they already carried, with a reference that is a function of the operation, so an old ledger replays to the same records. The new `decisionRecords` Host Remote lists one Task's records, oldest first, and the new `AgentTeamDecisionRecord` view carries them; the issue view's decision region is assembled by the issue-view card. MOCT's memory `decision` type is the projection target for the follow-on, not the store.
- Team Doc section writes are limited to the Doc's author and the Human (human decision, 2026-10-16): any other Member who calls `team_doc write` gets `only the Doc's author or the Human can write Doc '<ref>'` and commits nothing. Commenting and resolving stay open to every Channel member. Enforced at write time only; replay does not re-check the writer, so a non-author write committed earlier still replays.
- Decision cards (#87): an Agent can ask the Human 1 to 6 questions on one card in a Thread with the new `team_ask` tool (single or multiple choice, 2 to 4 options each, a recommended pick, and a written answer on every question), instead of asking in prose. The card shows in the Thread with radio and check boxes and a Send button; an open card is a mention in the Human's Inbox, the answer wakes the asker, and the asker can withdraw a card it no longer needs. A Doc in review is a plan card with Approve and Revise in its Thread and Channel. `team_ask` and `team_doc` submit wait up to 10 minutes for the answer or verdict; with none, the Agent goes ahead on its recommended options or the submitted Doc and stops before any step no one can undo. No new ledger operation: ask, answer and withdraw ride on Thread replies.
- Team Documents, editing and review (#95): the Human can edit a section on the Doc page (heading and Markdown, Ctrl+Enter saves, a section someone changed meanwhile shows the newer text before a second save), open its history and restore an older version as a new one, and resolve a comment thread, which folds it away and withdraws its pending comment. Open comments' passages are highlighted in the text. The Channel lists its Docs as cards under its header. A review verdict names any section the Human edited since the author's submit; `team_doc` gains `resolve` and `history`, and `read` marks Human-edited sections. One new ledger operation (`team/doc-comment-resolved`); section writes now record their writer, Human or Agent.
- Two lanes (#88): opening a Thread from its Channel keeps the Channel in view, with the Thread in a side lane beside it, the way a project chat keeps a thread open next to it. Drag the split or use the arrow keys on it (the width is remembered in this browser); Close or Escape closes the lane and returns focus to the Thread's row, which is marked as the open one. Inbox rows open the Thread the same way, and a reload restores both lanes. A seat under 900px wide (including phones) still shows the Thread alone. Client only; an embedded Member Session still takes the whole seat.
- Team Documents (#95, first half of #87): an Agent can write a plan or proposal as a Doc in a Thread with the new `team_doc` tool (outline first, one section per call, then submit), and the submit puts it in the Human's Inbox as a mention. The Thread shows its Docs as cards; a card opens the Doc on its own page, where the Human selects text to comment, leaves as many comments as needed, and then presses Approve, Review or Cancel. Review sends the pending comments back to the author and wakes it; every verdict is fenced by the Doc revision on screen. Three new ledger operations (`team/doc-created`, `team/doc-section-written`, `team/doc-comment-added`); submit and verdict ride on Thread replies.
- Per-Thread Sessions (#92 step 4): with `AGENT_TEAM_TASK_SESSIONS=own` on the Host, a new Task Thread for a multi-instance seat takes an idle extra instance slot before slot 0, so Task work runs in a Session of its own and the home Session keeps DMs and coordination; slot 0 is its last idle choice, and with every slot busy it queues on slot 1. Off by default, because extra slots have no recovery, rollover or pressure management yet; without it, and for plain Threads, routing is unchanged. `forkMemberSession` is implemented for the `summary` seed: it moves one Thread onto a fresh Session of the same seat (an extra slot with no live Session, else an idle one it ends first), rebinds the Thread to that slot and Session (`thread-session-bound` reason `fork`, parent = the source Session), and opens the Session with the Thread's summary and last 10 Messages; new messages in the Thread then go there. It now takes `requestId` and a required `threadRef`, and refuses a one-instance seat, a busy seat, a Session the seat does not own and the `full` seed. No new op kind or schema; the MOCT backend projects both bindings as before. No Client control yet.
- Task #16 PR 2: every instance of a multi-instance seat may now write its seat memory (`memory.md`): a per-seat revision lock (`seat-memory.ts`) refuses a write with `stale-memory` when the file moved since the Session last read it, and returns the current file to re-apply; a Session's revision is seeded when it starts and refreshed every step from the injected memory block and from each refusal, so a retry after a refusal passes (replaces the slot-0-only write refusal). A delivery now binds each delivered Thread to the Session carrying it (`start` the first time, `cold-restart` with a `stale-binding` log line when the seat runs another Session; the bind reason list is unchanged). A seat's warm Turns can be limited (`configureWarmLimit`, contract default one per minute; off until configured, so wakes start at once as before): a second delivery inside the window is coalesced into one deferred delivery that carries every fact that arrived meanwhile. `resumeMemberSession` with no live Session now resolves with `action: 'not-resumed'` and `coldFallback: { cause: 'no-handle', triedWarm: false }` instead of throwing (nothing was resumed or seeded). Not done yet: the `cache-cold` and `resume-failed` causes are declared but not produced.

The bind reason list is unchanged; the cause rides the result and the log only.
