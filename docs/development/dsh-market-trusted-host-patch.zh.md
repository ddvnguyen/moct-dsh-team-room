# dsh-market 受信任权威补丁

[English](dsh-market-trusted-host-patch.md) | 中文

## 为什么需要补丁

dsh-market 的普通路由通过 `sameOrigin` 承认主机**声明**的权威（`dsh web --trusted-host <name>`）。它的特权路由——备份导出、自卸载、一键重启——却不承认：它们要求一个直连的 loopback 对端。

经 Cloudflare 隧道访问的 lane 会拨号 `10.88.0.1:318x`，于是对端是代理，所有特权路由返回 403，而所有普通路由返回 200。用户没有办法满足这条规则：隧道的对端永远不是 loopback。

补丁让特权路由采用与普通路由相同的权威规则，同时保留所有保护措施：未声明的名字仍然被拒绝，loopback 的 `Host` 仍然必须来自 loopback 对端，标记为跨站的浏览器直接被拒绝，存在的 `Origin` 仍然必须与 `Host` 一致。

## 补丁是什么

三个文件，它们之间的分工很重要：

- `scripts/dsh-market-trusted-host-patch/edits.mjs` —— 带锚点的编辑，每个文件一组，安全论证就写在旁边。
- `scripts/dsh-market-trusted-host-patch/apply.mjs` —— 应用器：带锚点、幂等、写入前先做语法检查，带 `--check` 与 `--verify`。
- `scripts/check-dsh-market-patch.mjs` —— 检查脚本，针对**真实的已发布包**运行。

编辑是带锚点的，而不是 diff：锚点未变的 market 版本无需新的补丁文件；锚点被移动的版本会带着该编辑的 id 大声失败，并且不改动已安装的包。

## 它镜像的上游改动

上游改动是 **dsh-market PR #958**，于 2026-10-20 从 `fix/956-serving-port` 合入 `main`。它带着同样的围栏改动并补完了 PR #956——后者未合并就被关闭（其基线是 `nightly1014`）。

上游为这个补丁引入的两个符号取了同样的名字——围栏自身模块里的 `declaredTrustedHosts`，以及重启围栏里的 `servedAuthority`——因此应用器能认出已经带上该修复的版本并原样放过。目前还没有任何发布版带上这个修复：`1.66.37` 与 `1.66.45` 都没有。

## 已发布包的两种形态

已发布的 `dshmarket` 处于两种形态之一，各自对应各自的期望：

| 形态 | 发布版本是什么 | 检查脚本断言什么 |
| --- | --- | --- |
| 未修复 | 发布版本尚未带上修复 | 补丁可应用；未打补丁的副本上 `--verify` 失败；锚点被移动时大声失败、报出编辑 id，并且不改动包 |
| 上游形态 | 发布版本带上了 PR #958 的修复 | 补丁是空操作：不写入任何内容，`--verify` 退出 0 |

无论下载到哪一种形态，检查脚本都会**同时**覆盖两种形态。未修复的包会先被打上补丁，再去掉应用器留在补丁文件旁边的原始备份——这正是带上了修复的发布版本所处的状态。应用器通过标记认出该状态并且什么都不写，因此上游发布版落地的那一天，这个检查依然通过。

## 这些决定

### `--verify` 证明的是标记，不是行为

**决定：** 保留这种分工。`--verify` 断言包带上了该修复——应用器查找的那个标记——而不断言围栏如何作答。

**理由：** 部署只能问"补丁落地了吗"，标记恰好就是这个答案。行为在能够对着真实产物观察的地方断言：`scripts/check-dsh-market-patch.mjs` 对着已发布的包，以及部署自己的探针在 lane 上。

**后果：** `--verify` 退出 0 并不是对围栏行为的断言。把它当成保证来读的人，先读这一节。

### 仓库不可达时检查脚本跳过

**决定：** 保留跳过（退出 0，输出里有 `skipped`）。

**理由：** 检查脚本断言的是关于已发布产物的事实，而拿不到该产物的机器无法对它做任何断言。硬失败会让每台离线开发机因为与补丁无关的原因变红。

**后果：** `npm test` 变绿**并不**证明补丁——跳过的检查也是绿的。在 PR #159 的头上 CI 并没有跳过：它下载了 `1.66.37` 并跑完了每一条断言。必须证明补丁的 CI 任务要检查日志里有没有 `skipped`，或者把检查脚本改成在那里失败——这是有意识的改动，而不是意外。

### `.orig` 备份落在已安装的包里面

**决定：** 保留备份，留在应用器放置它们的位置——被修补文件的旁边。

**理由：** 它们是应用器用来比对的原始副本，也是唯一不需要仓库的回滚来源。

**后果：** lane 上的 `dshmarket` 副本会多出 `lib/http.js.orig` 与 `lib/restart.js.orig` 这两个已发布包没有的文件。没有任何东西 import 它们，而部署的回滚——移除被修补的目标并重新安装它——会把它们清掉。train 仓库里的部署 runbook 用一行说明这件事。

## dshmarket 发版时检查什么

1. `npm run check:market-patch` 下载已发布版本，并打印它找到的是哪一种形态。
2. 未修复的版本若移动了锚点，检查脚本会带着该编辑的 id 失败：调整锚点，不要重写编辑。
3. 上游形态意味着补丁已经没有事可做——lane 可以在之后的一次改动里去掉打补丁这一步。
